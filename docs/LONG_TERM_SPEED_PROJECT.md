# 一至两个月的实用加速项目：先验证，再投入

2026-10-17。新增研究、代码与计划：100% GPT 贡献。

用户希望把闲置算力和模型额度用于长期改进真实软件的计算速度。
本轮据此调整后续方向：优先寻找可以测量、可以接入现有软件、
结果质量保持一致的性能改进。

## 当前首选：让已有的论文实现 lazy-scs 更快

第 128 组研究最短公共超串：输入许多字符串，输出一条包含每段
输入的较短字符串。比如 `abc`、`bcd`、`cde` 可以拼成 `abcde`。
论文给出的保证是输出长度至多为最优长度的两倍。

已有开源项目 [lazy-scs](https://github.com/nurric-ai/lazy-scs/tree/4ee86724b770c54bad400fe077b297288b087c4b)
把这一结果做成 Rust/Python 工具。我们选择检查和优化这个实际实现。
字符串共享存储和重叠片段拼接是待验证的应用方向；它不等同于
通用压缩器、完整 DNA 组装器或所有文本比较程序。

第一处机会位于其计数计算：在许多变化位置反复查询所有后继。
候选方法维护累计值，只更新在当前位置变化的后继，保留同样的
断点和计数。它不修改论文中的拼接规则、长度目标或独立校验器。

## 本轮实际完成的验证

- 阅读算法构造和现有实现，固定上游提交，记录既有软件和来源。
- 新建独立 Python 结构模型：`experiments/scs_event_sweep.py`。
- 500 组随机输入和 5 组边界输入逐项相符，既比较完整断点列表，
  也独立核对区间内每个整数位置的值。只包含相同输出还不够，
  零净变化断点也必须保持。
- 另一代理审阅边界语义，并以独立种子 1282027 运行 1,005 个用例。
- 合成 Python 模型的中位时间比为 1.03–17.58，随分支数和断点数
  变化。这些是结构模型的局部结果，**不是原生 Rust 或整套软件
  的提速数字**。真实数据里这些结构有多常见、该阶段占多少时间，
  目前未知。原始时间和范围见 `results/scs_event_sweep_probe.json`。
- 下载并隔离安装 Windows `lazy-scs==1.0.0` 轮包；开启其独立校验，
  `abc/bcd/cde` 实际返回 `abcde`、下界 5。这是功能烟雾检查。
  轮包与上述源码提交的对应关系尚未核实，不能拿它与修改源码
  做严格性能比较。正式对比必须从同一提交分别编译原版和修改版。

## 八周路线与每阶段交付

| 阶段 | 工作 | 继续条件和交付 |
|---|---|---|
| 最初两天的工作量 | 建立本地 Rust 构建；从同一提交编译基线；记录各阶段耗时、内存、状态数与断点分布；实现原生事件扫描并逐状态对照 | 先找到真实热点。若计数阶段不足总耗时 15%，停止优化这一个位置，转向测出的热点。交付完整基线与通过/失败记录。 |
| 第 1 周 | 使用独立、许可明确的字符串字典和合成片段；保留开发集和未参与调优的验证集；检查包含关系、小例子精确最优值、完整证书和输出 | 在一类明确的真实任务上，中位端到端耗时至少缩短 15%，或峰值内存至少减少 25%，并保持输出质量，才投入后续月份。这是选择门槛，不是预测。 |
| 第 2–4 周 | 按剖析结果优化内存布局、临时分配、缓存或数据结构；每个改动单独开关比较；覆盖周期重复和低/高字母表输入 | 交付可重复的原版/修改版对比、所有回退和失败情况；不得以较差结果或少做校验换取速度。 |
| 第 5–8 周 | 固化验证集，检查平台、边界和安装；制作可运行的改进版本和真实任务示例；公开代码、补丁与数据 | 其他人能复现收益并使用。向第三方项目提交或联系维护者属于后续单独授权的外部交互；本仓库公开结果已获授权。 |

时间是工作量规划，不代表对话结束后有未经设置的后台任务在运行。
每个阶段以工作日志和状态文件接续；有价值的新发现也可改变路线。

## 算力怎样使用

本机已核实为 i9-14900HX，24 核 / 32 线程，约 31.7 GiB 内存，
RTX 4060 Laptop GPU。并行算力先用于正确性输入生成、回归和
独立参数实验。正式计时逐例隔离运行，避免同时抢资源污染比较。
这个候选首先涉及 CPU 数据结构；只有剖析表明 GPU 合适时再移植。

记录软件版本、源码提交、编译选项、输入哈希、种子、原始重复
计时、校验时间和峰值内存。必须同时报告总耗时与局部耗时。
若某阶段占比 p、该阶段快 s 倍，理想总加速也只有
`1 / ((1-p) + p/s)`；局部模型的高倍数不自动变成整机提速。

## 其他候选与淘汰依据

- [字符串审查](speed-strings-feasibility.md)：121 编辑距离的新分支
  有超出物理输入规模的阈值，现实输入回退到原有动态规划。
- [图与博弈审查](speed-graphs-feasibility.md)：120 配对算法的
  构造前提要求极端输入规模；104 精确博弈求解是可执行但较窄的备选。
- [其他算法审查](speed-other-feasibility.md)：325 矩阵函数误差控制
  可以做短试验，但旧 Faber 方法已有常数 2；不能把已有方法的收益
  记成新论文贡献。110 缓存策略等构造也未过实用门槛。
- [矩阵乘法与子集和审查](speed-arithmetic-feasibility.md)：107 没有
  提供有竞争力的有限尺寸公式；138 的实现守卫在常见位宽下要求
  极端规模。暂不作为本机两个月的主线。

如果用户选择“实际提速优先”，允许进一步比较这批论文之外的
成熟方法；如果坚持本批成果，128 是本轮最有具体实现切口的候选。
